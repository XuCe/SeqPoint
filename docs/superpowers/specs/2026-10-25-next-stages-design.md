# 后续阶段设计草案（2026-10-25）

依据 `.codex/TODO.md` 的阶段顺序；本轮仅列设计，不修改业务代码。以下是建议，尚未视为用户确认。

## 范围与原则

近期按桌面收尾 → 提醒闭环 → 备份与恢复推进。沿用 Flutter/Dart、现有服务和设置组件；不重构无关代码。
阶段 4–6 只界定交付边界，进入阶段时再设计接口。同步遵循《同步架构方案 V1》的单写者加密文件方案。
现有工作区含桌面常驻相关未提交改动，后续实现须保留。每次代码修改 ≤50 行、单文件校验后才推进下一项。

## 1. 桌面收尾：先补验，再修复

目标：主窗口关闭后仍可找回，主动退出后全部窗口及进程结束。

| 场景 | 设计与验收 |
| --- | --- |
| 原生关闭 | 主窗口隐藏，保留草稿与全局绑定；便签子窗口保留自身关闭语义 |
| 真实快捷键 | 隐藏后逐一验证唤起、新建、剪贴板、搜索；编辑中触发保护当前草稿 |
| 托盘唤起 | 主窗口重新显示并获得焦点，重复点击不创建第二个主窗口 |
| 托盘退出 | 分别在无子窗、有便签子窗、注册尚未结束时退出；进程结束且快捷键释放 |
| 托盘失败 | 主窗口可正常关闭退出，不留下无法找回的后台进程 |
| Windows | 在真机重复同一组场景，不能用 macOS 结果代替 |

已有自动化与 macOS 进程检查是历史证据；真实按键、托盘点击、带子窗退出、Windows 尚需实测。
本阶段只修复可复现问题；快捷键自定义、系统占用冲突检测、开机启动不加入本次范围。
设备不可用时保留“未验收”记录，可以推进其他阶段设计与开发，不能宣布桌面全平台验收通过。

## 2. 提醒闭环：业务状态驱动系统调度

目标：到期可提醒，改期撤旧，完成/删除即取消，重启可恢复，点击能定位。
首批交付现有事项期限对应的精确/相对提醒；智能追加、忽略降频和晚间汇总后续分批接入已有策略。

建议链路：保存事项 → 持久化提醒计划 → 平台安排通知 → 点击后读取当前事项 → 打开原便签并定位事项。
复用 ReminderRepository、现有提醒策略与 NotificationService；只由主应用调度，便签子引擎不重复注册。

| 事件 | 处理 |
| --- | --- |
| 新建/改期 | 以事项 ID、提醒类别、计划时间确定计划身份；取消旧计划，按最新数据安排 |
| 完成/放弃/删除事项 | 撤销相关待发计划；删除整张便签时连带处理事项 |
| 启动/恢复前台 | 对账数据库计划与平台调度，清理失效项、重建有效项；本机去重身份持久化 |
| 点击通知 | 唤起主窗口并查询当前状态；已删除或已完成时提示当前状态，不恢复旧任务 |
| 权限拒绝/调度失败 | 事项照常保存，显示通知未启用或待重试；重试复用同一计划身份 |

计划必须保留可重试状态；不能先标记成功再调用平台，也不能让失败计划消失。重启取消不能仅靠内存映射。
现有通知接口还需补齐冷启动点击接收及跨重启对账能力；原生权限、时区、精确定时能力逐平台验证。
现有 ReminderEngine.planFor 只计算当前可触发计划，不能直接用于未来通知预排；实施时补齐未来时间计算与持久化计划协调。
重建调度需读取全部有效事项，避免沿用 openAll 默认 500 条的页面限制。首批采用默认策略，设置可编辑与持久化另拆。

提醒语义建议：用户指定的时间不因智能策略推迟；智能提醒沿用既有勿扰与频控，不另写规则引擎。
重启时已过期的计划建议合并为一条补提醒，避免逐条轰炸；该策略是本草案的选择，实施前列入用例。
“只提醒一次”指同一计划不重复安排；系统通知没有送达回执，不能承诺崩溃/系统限制下严格恰好送达一次。
应用退出后能否准时提醒依赖各平台的原生调度，不能用后台 Dart 定时器代替平台验证。
验收：新建、连续改期、完成、删除、恢复、重启、时区变化、拒绝权限、冷启动点击；按单项和单文件逐步校验。
删除后恢复仅重建仍有效的未来计划；已取消、已完成和旧时间的通知不得重新出现。

## 3. 备份与恢复：先保护本机数据

入口：沿用设置分类，提供“立即备份”“本机快照”“导出 JSON / Markdown”“从本机快照恢复”。
JSON / Markdown 是供阅读的明文导出，不作为数据库恢复输入；取消目录/文件选择不写入文件。
首批导出范围固定为全部未删除便签（含归档）及其事项/关联标签；排除 secrets，并过滤被排除对象的关联记录。
现有 JSON 的 includeArchived 尚未生效、关联表过滤不完整；接入口前修正范围一致性，不增加导入功能。
快照列表展示创建时间、大小、格式与校验状态；复用 SnapshotService 的 SQLite 快照，不另造数据备份格式。
当前实现未显式加密。本草案建议首批如实标为“未加密本机快照”，不宣称符合 PRD 的加密备份验收。
该分期范围需要用户审阅；若本阶段必须达到 PRD 加密要求，应先完成密钥生命周期设计，再开放备份入口。
SQLite 快照含库内全部表，包括设备/同步状态与 secrets 表的密文；不包含系统安全存储和库外附件文件。
首批恢复验收限定便签、事项、标签；界面说明当前范围，不能称为含附件与可用凭据的完整换机备份。

恢复流程建议：
1. 先只读验证所选文件的 SQLite 完整性、可支持版本和必要表结构；损坏或未来版本在停写前拒绝。
2. 展示备份时间和数据范围，明确“替换当前本机数据”；用户确认后执行，重复点击只运行一次。
3. 在主引擎暂停写入和通知调度，要求便签子窗完成保存/取消并关闭；仍有未保存输入则中止恢复。
4. 生成并校验恢复前保护快照，复制候选到同目录暂存文件；任一步失败均保留当前数据库。
5. 关闭所有数据库连接，使用可回滚的文件替换；旧库及 SQLite 辅助文件需正确处理，不能直接覆盖活跃库。
6. 用候选库重建 Bootstrap/AppScope 并验证可读；失败则回滚并重开旧库，成功后才刷新主界面与重建提醒。
7. 进程中断后，下次启动先判定恢复是否完成；未完成时恢复旧库。恢复状态与文件替换需有最小持久化标记。

现有 restore 仅检查最低 user_version 并直接 copy，以上校验、停写、原子替换、回滚与容器重建均属于待实现项。
正常备份采用现有同日快照保护逻辑；手动操作不得覆盖上一份有效文件。导出先写临时文件，成功后再完成保存。
首批不启动自动清理；原快照保留策略沿用现有上限，保护快照在恢复确认成功前不得删除。
可携带的加密备份、Recovery Key、云备份与自动定时备份后续单列，避免把本机 SQLite 文件误作换机方案。
验收：便签/事项/标签往返一致；损坏/缺表/未来版本拒绝；空间不足、停写失败、替换失败、重启失败与中途崩溃后旧数据仍可打开。
