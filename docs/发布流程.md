# 发布流程

GitHub 仓库：[XuCe/SeqPoint](https://github.com/XuCe/SeqPoint)。
日常提交运行 `.github/workflows/ci.yml`；发版运行 `release.yml`；热补丁运行 `shorebird-patch.yml`。
Android/macOS/Windows 自动生成安装包；iOS 自动编译未签名归档，暂不签名分发。
原有 Linux arm64 构建继续保留。

## 前提

1. 当前功能、依赖、`shorebird.yaml` 和工作流须先提交并推送到 GitHub；不能只上传工作流而遗漏应用改动。
2. Settings → Secrets and variables → Actions 配置 `SHOREBIRD_TOKEN` 及下文四项 Android 签名 Secrets。
3. 仓库启用 Actions；工作流默认只读，仅创建 Release 的 job 显式申请 `contents: write`。
4. 使用 GitHub 托管的 Ubuntu、macOS、Windows Runner，不依赖之前的 GitLab Ubuntu Runner。
5. iOS 暂不需要分发证书；其任务始终使用 `--no-codesign --dry-run`，不会上传正式 Shorebird iOS 基线。

## 发布一个版本

```bash
# 1. 改版本号
#    apps/seqpoint_app/pubspec.yaml 的 version: 0.1.0+1

# 2. 打 tag 并推送
git tag v0.1.0
git push origin v0.1.0
```

推送后自动执行：检查与测试 → 各平台并行构建 → 汇总产物 + 生成 SHA256 → 创建 Release。
tag 的版本必须与 `pubspec.yaml` 去掉 `+build` 后的版本一致，否则停止发布。
tag 名里含 `-`（如 `v0.1.0-beta`）会被标记为预发布。

想先验证流水线本身而不真的发布，用 Actions 页面的 “Run workflow” 手动触发：
它会走完构建但跳过创建 Release；Shorebird 使用 `--dry-run`，不会上传发布基线。

| macOS arm64 | `seqpoint-<版本>-macos-arm64.dmg` | 19 MB |

体积说明：这些是 release 包。开发时的 debug APK 有 158 MB，
因为含全部 ABI 与调试符号，**不代表发布体积**。

## 签名

### Android：已配置 ✅

发布密钥已生成并接好，release 构建自动使用它。

| 项 | 值 |
|---|---|
| keystore | `apps/seqpoint_app/android/seqpoint-release.jks` |
| 配置 | `apps/seqpoint_app/android/key.properties` |
| 别名 | `seqpoint` |
| 算法 | RSA 4096 / SHA384withRSA |
| 有效期 | 10000 天（约 27 年） |
| 签名方案 | v2 + v3（minSdk 26 用不到 v1） |
| 证书 SHA-256 | `D2:C8:57:25:B4:4A:9E:3B:5D:91:1D:E2:0D:48:9C:31:B3:77:24:F2:95:08:60:63:B9:AD:91:E2:0D:71:38:EF` |

**这两个文件不在 git 里**（见 `.gitignore`），换台机器或重装系统就没了。

> ### ⚠️ 必须立刻备份
>
> **keystore 一旦用于发布就不能更换。** 丢了它或忘了密码，等于永远无法为
> 已发布的应用推送更新——只能改包名重新上架，老用户全部失联。
>
> 请把 `seqpoint-release.jks` 和 `key.properties` 一起备份到至少两个地方，
> 例如密码管理器的附件、加密网盘、离线 U 盘。**别只放在这台电脑上。**

没有 `key.properties` 时（新克隆的仓库、CI 未配 Secret），构建会自动回退到
debug 签名：能跑能装，但不能上架，也无法与正式版互相覆盖升级。

#### CI 签名

流水线通过四个 Repository Secret 拿到密钥。正式 tag 发布缺任何一项就失败；
仅手动预演允许 debug 签名。已配置密钥时，构建后会验证产物不是 debug 签名：

| Secret 名 | 内容 |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | keystore 的 base64（`base64 < seqpoint-release.jks`） |
| `ANDROID_STORE_PASSWORD` | key.properties 里的 storePassword |
| `ANDROID_KEY_ALIAS` | `seqpoint` |
| `ANDROID_KEY_PASSWORD` | key.properties 里的 keyPassword |

配置位置：仓库 → Settings → Secrets and variables → Actions → New repository secret。
四项的现成值已导出到 `~/Desktop/seqpoint-github-secrets.txt`，**配完请删除该文件**。

## 已知限制

- Linux 只构建 arm64。若还要 x64，复制 `linux` job 改 `runs-on: ubuntu-latest`
  并把产物名里的 `arm64` 改成 `x64`。
- iOS 已自动编译，但仅产出未签名 `.xcarchive`；不能直接安装，也没有正式热更新基线。
- 将来签名分发前，需要配置对应 Apple 证书/描述文件并选择 TestFlight、App Store 或 Ad Hoc。
- 构建缓存靠 `subosito/flutter-action` 的 `cache: true`，首次会慢一些。

## 四端热更新（Shorebird）

Android、iOS、macOS、Windows 共用一个 Shorebird 项目，各平台分别建立发布基线、分别推送补丁。
桌面「设置 → 应用更新」和移动端「我的 → 应用更新」可检查及下载补丁；
默认启动时也会后台自动下载，下次完整启动生效。桌面必须从托盘退出，关闭窗口不等于退出。
不会强制退出应用。普通 Flutter/debug 构建显示「热更新不可用」。

### 项目配置（首次发布前检查）

已创建 SeqPoint 项目，真实 app_id 为 `7521be30-6088-44fe-824c-5f1622031be7`。
`apps/seqpoint_app/shorebird.yaml` 已配置并加入 Flutter assets，四端共用，自动更新已开启。
无需再次 `shorebird init`。安装 [Shorebird CLI](https://docs.shorebird.dev/getting-started/) 后执行：

```bash
cd apps/seqpoint_app
shorebird login
shorebird doctor
```

保留 `shorebird.yaml` 中的 `auto_update: true`；不要用 `init --force` 创建不同 app_id。
app_id 可以入库；登录令牌不可入库。API key 可通过环境变量 `SHOREBIRD_TOKEN` 使用。

在 GitHub Actions Secrets 设置 `SHOREBIRD_TOKEN`（从 Shorebird 控制台创建 API key）。
现有 Android 签名 Secrets 仍需配置；Apple 签名配置不由 Shorebird 替代。
CI 未配置令牌前，Shorebird 发布构建不能完成；不会回退生成不支持热更新的安装包。
使用 `shorebird flutter versions list` 确认 CI 固定的 Flutter 3.47.2 可用。

Android/macOS/Windows 的 tag 发布已改为 `shorebird release`，保持原 APK/DMG/ZIP 分发渠道；
Linux 保持普通 Flutter 构建。Android 改为包含两种 ARM ABI 的单个 APK。
iOS 当前只做 CI 未签名预演。将来在 Mac 配置 Xcode 签名后，才使用下一节的 iOS 正式命令。
现有普通 Flutter 安装包必须先完整安装一次 Shorebird 基线包，之后才可接收补丁。

参考：[初始化](https://docs.shorebird.dev/code-push/initialize/)、
[支持平台](https://docs.shorebird.dev/concepts/)、
[CI 配置](https://docs.shorebird.dev/code-push/ci/github/)。

### 手动热补丁工作流

在 GitHub Actions 选择 `shorebird-patch` → Run workflow：

- `platform`：android / macos / windows；iOS 签名基线尚未启用，暂不提供此选项。
- `release_version`：已发布的完整基线版本，例如 `0.1.0+1`，禁止填 latest。
- `track`：默认 staging；改为 stable 才面向正式客户端。
- `dry_run`：默认 true，只编译验证；取消后会上传到所选 track。

工作流先运行分析/测试，Android 复用正式签名。staging 验证通过后，可在 Shorebird Console
将该补丁推广到 stable。基线发版和热补丁是两条独立流程，不要为热补丁递增应用版本号。

### 本机发布与补丁（iOS 正式命令待签名就绪后使用）

在 `apps/seqpoint_app` 目录运行；macOS/iOS 使用 Mac，Windows 使用 Windows。
新基线需递增 `pubspec.yaml` 的 `version`（含 build number），补丁沿用目标基线版本。
下面是手动发布方式；已经由 tag CI 建立的同平台/版本基线，不要再重复 release。

```bash
shorebird release android --flutter-version 3.47.2 --artifact apk --target-platform android-arm,android-arm64
shorebird release ios --flutter-version 3.47.2
shorebird release macos --flutter-version 3.47.2
shorebird release windows --flutter-version 3.47.2
```

安装并分发上述生成的 APK / IPA / .app / Windows bundle，不能再用普通 `flutter build` 覆盖它们。
iOS 的 IPA 仍需上传 App Store Connect；Shorebird 不会替代商店提交或安装。

仅修改可热更新的 Dart 代码后，为每个平台单独发补丁（将版本替换成实际基线）：

```bash
shorebird patch android --release-version 0.1.0+1 --track staging
shorebird patch ios --release-version 0.1.0+1 --track staging
shorebird patch macos --release-version 0.1.0+1 --track staging
shorebird patch windows --release-version 0.1.0+1 --track staging
```

用 `shorebird preview --platform <平台> --release-version 0.1.0+1 --track staging` 验证。
通过后在 Shorebird Console 将对应平台/版本的补丁推广到 `stable`，正式客户端只检查 stable。
异常时在同一控制台停用/回滚对应补丁；客户端下次检查、完整重启后生效。
不要省略目标版本而误推其他基线；patch 会自动复用该基线的 Flutter 版本。

验收：分别安装四端真实基线包 → 发布可辨认的测试补丁 → 检查/下载 → 完整重启 → 确认变更。
同时验证断网提示、恢复网络后重试。iOS 必须使用真机，模拟器不能验证 Shorebird 补丁。
插件原生代码、权限、原生配置或资源变化需完整发布，不能依靠热更新。
本地 widget 测试只能证明页面状态与异常处理，不能证明真实补丁下载及跨平台安装成功。

参考：[发布基线](https://docs.shorebird.dev/code-push/release/)、
[发布补丁](https://docs.shorebird.dev/code-push/patch/)、
[预览](https://docs.shorebird.dev/code-push/preview/)。
